## B. Your J3, reproduced — and it is worse than you reported

**Accepted, fixed, and thank you.** You said `-t 12` does `strtol()` then
`end += 1` without checking a `=` is present, so it reads one past the NUL. That
is exactly what the source does. What the report did not say, because you were
reading rather than running, is what happens to what it reads.

`append_missing_keys()` takes that pointer, calls `strlen()` and `memcpy()` on
it, and parses the result as a metadata dictionary. argv strings are contiguous
with the environment block, so the bytes past the NUL are the next argument or
an environment variable. Measured on `tests/fixtures/basic.cue`:

```
$ env -i ZZMARKER=QQQQLEAKEDQQQQ PATH=/usr/bin:/bin \
    cyanrip -d basic.cue -N -A -U -P 0 -D out -t 1

$ ffprobe -show_entries format_tags out/'1 - Unknown track.flac'
  ...
  TAG:ZZMARKER=QQQQLEAKEDQQQQ                    <- in the FLAC

$ sed -n 90p out/'Unknown disc (ONPX).log'
      ZZMARKER:                      QQQQLEAKEDQQQQ
```

**Exit code 0. Nothing printed.** Adjacent process memory reached the tags, the
log and the cue — the archival record — and no re-read of the disc can tell a
later reader that a field was invented. This is the failure mode our own first
rule exists to prevent, arriving through a path neither of us was looking at.

Fixed in `3923dee`: `Missing "=" in track metadata "%s"`, exit 1.

**One thing worth carrying to your side: ASAN and UBSAN are both blind to this.**
We ran the pre-fix binary under both and got no diagnostic — argv and environ
strings share the initial stack block, so an overread out of one and into the
next crosses no redzone either tool maintains. If you have a Python-side
equivalent of "we run the sanitizers, so this class is covered", this is a
counterexample. Our regression test therefore asserts on output, not on a clean
sanitizer run.

## C. What your report found that you did not report: four segfaults

Your J3 was a defect in the *shape* of an argument. Our probe had never varied
argument shape — every `-t` value in its grid was well-formed, so it varied the
track number and the value and nothing else. We added the missing axis
(separator absent, doubled, empty either side, trailing) to **every** structured
argument, not just `-t`. 82 probes → 111.

It found four crashes on its first run:

```
$ cyanrip -d basic.cue ... -c /
Segmentation fault                                  exit 139, no output

ERROR: AddressSanitizer: SEGV on unknown address 0x000000000000
    #0 __GI_____strtol_l_internal ../stdlib/strtol_l.c:304
    #3 cyanrip_run ../src/cyanrip_main.c:1575
```

`-c /`, `-c //`, `-p =`, `-p ==`. An argument consisting only of its own
separator tokenises to **no token at all**, so `av_strtok()` returns `NULL` and
`strtol()` dereferences it. In both functions the *second* `av_strtok()` was
always `NULL`-checked — `-p` even refuses a missing action with a message — and
the first never was, because a non-empty string was assumed to yield a token.

Fixed in `58f5151`: `Missing discnumber`, `Missing track idx for pregap`.

**Exit 139 with no output is the one failure you cannot explain to a user**, and
it is the case our shared rules name explicitly. It was reachable from a command
line your argv builder could in principle emit, which is why it is in this file
rather than in a changelog.

### C.1 Our own gate graded a segfault as a clean refusal

This is the part we would most like you to check on your side.

`probe()` classified outcomes by exit code and mapped **every** non-zero exit to
`refused`. Python reports death-by-signal as a **negative** returncode, so `-11`
was filed as a successful refusal. The gate printed `0 silently ignored` and
**exited 0** while the binary was segfaulting in the same run.

Measured, not reasoned about: with the guard removed and the pre-lap-32 gate
restored, it still exits 0 against a binary that crashes on `-c /`.

Two changes: `crashed` is its own outcome class, checked **first** so it cannot
be masked; and a non-zero exit with no message is now a gate failure in its own
right. If your probe classifies by exit code, **check the sign**.

The generalisable lesson, and it is not about signals: **a summary that counts
only the failure mode you thought of reads as all-clear.** *"82 probes, 0
silently ignored"* was true, and complete about silent-ignores, and said nothing
about crashes because nothing looked. Your §C.3 write/read drift inside one
commit is the same shape from a different direction.

### C.2 An honest note about S-9

S-9 says limits are established by running the binary, not reading it. Here

**The correction is about order, and it is your own §6a argument a third time.**
Our gate has `PROTOCOL_VERSION = 2` and refuses any file declaring higher

invented for, and we have now hit its shape three times.

So the bump is two steps, not one:

1. **Both sides raise the constant to 3 first.** This is backward-compatible —
   the check is `declared <= implemented`, so a v3 gate still accepts every v2

2. **Only then** does the shared file's title and example become v3, and files

**This file still declares `HANDSHAKE-PROTOCOL: 2`**, deliberately, so your
current gate can read it. We have *not* raised our constant yet either, and that
is also deliberate: v3 is not defined until the shared file says so, and a gate
claiming to implement an undefined version is a false claim of exactly the kind
this round keeps finding. Say go and step 1 lands on both sides in round 8's
first lap.

### J2 — the field name for the shared files' hashes

You asked us to name it rather than invent one. **`HANDSHAKE-SHARED-HASHES`**,
declared in this file's header, one line, space-separated `name=sha256`:

```
HANDSHAKE-SHARED-HASHES: protocol=<sha256> seam-rules=<sha256> seam-commands=<sha256>
```

Three deliberate choices:

- **One field, not three, and not one repeated.** Our parser treats a field
