## A. Correction to lap 1 — a claim we made that the evidence did not support

Lap 1 §D1 and §F both state, of the first `-x` run on real hardware:

> *"a hit at 32 and a **miss** at 64"*

**That is wrong.** It was not a miss. The 64-sector read **failed**, and the
drive's cache is far larger than 64 sectors.

The evidence arrived tonight, from the cross-check lap 1 §F itself said had not
been run. `cd-paranoia -A` on the same drive and the same disc:

```
Analyzing cache behavior...
        Approximate random access cache size: 137 sector(s)
        Drive cache tests as contiguous
        Drive readahead past read cursor: 119 sector(s)
        Cache tail rollbehind: 112 sector(s)
        Backseek flushes the cache as expected
```

**137 sectors.** Our probe stopped at 32 and could not have got further, for a
reason that is ours and not the drive's: it issued the whole forward run as a
single command, and 64 sectors is 150,528 bytes, while an `sr` device's
`max_sectors_kb` is commonly 128 KiB. The read could not succeed at any cache
size.

Two things follow, and they are different:

- **The reported figure was never contradicted.** "At least 32 sectors" is true
  and remains true; 137 satisfies it. What was wrong is lap 1's *description*
  of how the search ended.
- **The pre-fix wording was worse than we knew.** On `ddf7ac3` this same event
  printed `Cache probe:    32 sectors measured`. The real answer is 137. That
  line would have entered an archival record asserting a number **wrong by a
  factor of four**, produced by a read error the sentence could not distinguish
  from a cache boundary.

So the wording fix in lap 1 did not make the probe correct. It made it stop
claiming something it had not established — which is the whole of its job, and
it did that job on its first hardware run. The correctness fix is this lap's.

## D. Log-format delta — no wording change

**The `Cache probe:` line's wording is unchanged from beta.1.** All nine forms
are as lap 1 described and as `tests/cacheprobe.c` pins them. What changes is
**which** of them a real drive produces, and the numbers in it.

`PROBE_CHUNK_SECTORS` is 25 — 58,800 bytes, under even a 64 KiB limit. A run of
N sectors is now however many commands that takes. The forward run is a warm-up
whose only purpose is to fill the cache; whether it arrives as one transfer or
several does not change what ends up cached, and cd-paranoia reports this
drive's cache as contiguous. A read that still fails at 25 sectors is a real
read failure and still ends the search, which is what that wording is for.

**No other line changes anywhere.** No fixture runs `-x` at all, so the golden
reference moved only in its banner, its three `comment:` tags, its `Handshake:`
line and the wall-clock fields.

## E. Falsifiable prediction — please check it, and tell us if it fails

On the rig's PIONEER BD-RW BDR-209D with this disc, beta.2's `-x` should report:

```
Cache probe:    128 to 255 sectors (...)
```

The search doubles, so a cache of 137 means a hit at 128 and a miss at 256, and
the bracket `[128, 256)` contains cd-paranoia's 137.

**Anything else falsifies this fix**, and we would rather hear that than have it
pass unexamined:

- another `read failed while growing the run` → the chunk size is still above
  some limit, or the failure was never a transfer cap;
- a bracket not containing 137 → our method and cd-paranoia's disagree about
  what a cache boundary is, and neither number can be trusted;
- `search ceiling reached` → the cache exceeds 2048 sectors, which would
  contradict cd-paranoia by an order of magnitude.
