# Platterpus: end-user experience review, 2026-11-17

Platterpus 0.7.127 (latest `main`, `0c649441`), checked out at
`/tmp/claude-0/-home-user-claude-code-skills/46cfbc1a-d1c5-5a09-bbbb-4b2444266d0f/scratchpad/ux/platterpus`.
One evaluator and two passes, so this is not the full `usability-review` method (rule 7).
The severity figures are one rater's, on Nielsen's 0 to 4 scale.

## How it was run

- **Installed** into a scratch venv (`ux/venv-pp`, Python 3.12, PySide6 6.11.3) with
  `uv pip install -e .[dev]`. I did not run `install.sh`, `setup-host.sh` or `dev-setup.sh`.
- **The real `app.main()`** ran under `QT_QPA_PLATFORM=offscreen`, with `HOME` and the XDG
  folders pointed into scratch. Every external command was refused, as on a machine with nothing
  installed (`ux/pp-run/drive.py`). A timer grabbed each top-level window whenever it changed and
  answered dialogs in a scripted order. Shots: `ux/pp-run/shots/run2` to `run5`.
- **Staged states** came from `ux/pp-run/stage.py`, which builds `MainWindow` with fakes, as
  `tests/test_ui_main_window.py` does. It shows a disc, a rip in progress, a finished rip parsed
  from a real 14-track log
  (`tests/fixtures/evidence/docs/handshake/artifactsround40/round40fullrepeatrip2.log`), a
  cancelled rip, an error, and the read-offset dialog. It ran in light mode
  (`shots/stage-light2`) and dark mode (`shots/stage-dark2`).
- **Not run:** a real drive or disc, the AppImage itself, the setup steps past their first
  command, the Breeze style (only Fusion is installed here). Dark mode used Fusion with a
  Breeze Dark palette.
- **Staging artifacts, not findings:**
  - The drive combo is empty in the staged shots.
  - The top table's titles are fakes, while the results table's come from the real log.
  - In `C`, the status text is mine, written in the app's own format
    (`workers/rip_worker.py:4410`). In `G`, the error text is mine.
  - The CTDB line in `E` is a match I staged, with no per-track data.

All screenshot paths below are relative to
`/tmp/claude-0/-home-user-claude-code-skills/46cfbc1a-d1c5-5a09-bbbb-4b2444266d0f/scratchpad/ux/pp-run/shots/`.

## 1. Top 10, in the order a first-time user would complain

1. Answering **No** to "Set it up now?" still opens the setup wizard. Three more dialogs follow
   it within 10 s, one of which reports "Install failures" for an install that never ran. First
   launch. Severity 3, effort M.
2. On a fresh install, the app opens a "cyanrip update" dialog on its own. It speaks of a
   "handshake round 40", "unapproved" rips and "no commit typed in". First launch. Severity 3,
   effort S.
3. The README spends 662 words before *At a glance*. Its *Status* paragraph alone is 317 words
   of release and round history. *Getting started* sits at line 541, after 450 lines of manual
   Distrobox steps. `README.md`. Severity 3, effort S.
4. When setup fails, the user sees raw exception text ("command not found: pkexec ([Errno
   2]…)") and no next step. The dialog also promises "usually instant" for a build the README
   says takes minutes. Setup wizard. Severity 3, effort M.
5. A finished rip says "Done." directly above an amber "AccurateRip says each is WRONG". The
   verdict names "frame 450" and never says what to do next. Main window, after a rip.
   Severity 3, effort S.
6. The main window's hierarchy is upside down. Disc IDs come first. There are two track tables,
   and the editable one shows 4 rows. Two progress bars sit one above the other, and only one
   has a label. Main window. Severity 2, effort M.
7. Settings is one ungrouped form of 33 rows that scrolls both ways. Its labels are jargon and
   its list items are in Title Case. Settings. Severity 2, effort M.
8. The results table's columns are "AR v1 / AR v2 / EAC". Its cells read "OK (129 of 200)", "one
   frame only (200)", or a hex CRC with ✓ or ~. Tracks tab. Severity 2, effort S.
9. A failed rip appears only as plain grey status text ("Error: …"), with no colour, icon or
   next step. Main window. Severity 2, effort S.
10. The read-offset step opens on a large empty box and calls cyanrip "this backend". It also
    titles both the question and the wizard "Set up Platterpus", and the question box ends in
    "Run setup….". First run. Severity 2, effort S.

## 2. Findings by area

### First run and onboarding

**F1. "No" doesn't mean no, and four modals arrive in a row** (severity 3, effort M). This
breaks *windows-and-dialogs* rules 1 and 3 and Nielsen's heuristic 3 (user control).

- **Evidence:** `run4/` and the app log `pp-run/home4/.local/share/platterpus/log.txt`. At 1.0 s
  comes "Set up Platterpus: … Set it up now?", and the user picks **No**. At 3.8 s the
  `HostSetupDialog` opens anyway (`run4/03-…png`). The log reads "delivering the held dependency
  report now → dialog presented: HostSetupDialog". At 6.6 s comes "Dependency check complete"
  (`run4/04`), and at 10 s "cyanrip update" (`run4/05`).
- **The cause:** the launch dependency check holds its report until the question closes. It then
  runs `_resolve_missing_unified`, which opens the wizard whatever the answer was
  (`ui/main_window_deps.py:542-578`).
- **What the user sees:** the app ignores their answer, then lists "Install failures: cyanrip:
  still missing after setup — re-run the wizard" (`ui/main_window_deps.py:882`), although no
  setup ran.
- **Fix:** treat the first-run answer as the decision for this launch. After No, show one
  non-modal banner in the main window: "Ripping tools aren't installed. **Set up…**". Then show
  no dependency summary and no cyanrip offer until setup has run. When nothing was attempted,
  word the summary as "Not installed yet", not "Install failures".

**F2. A ripper-update dialog nobody asked for, in maintainer language** (severity 3, effort S).
This breaks *windows-and-dialogs* rule 1, Nielsen's heuristic 2 (match the real world) and
*usability-review* rule 3.

- **Evidence:** `run2/05-QMessageBox-cyanrip_update.png`, which is shown on every fresh launch
  in these runs. It reads "Expected: 0.9.4-rc3+platterpus.32 (edb73dd) — the build handshake
  round 40 approved, for Platterpus 0.7.125". It goes on: "every rip reports its ripper as
  'unapproved' … whether the record can say the ripper was jointly verified … needs no commit
  typed in."
- **The problems:** the window title says 0.7.127, yet the dialog says "for Platterpus 0.7.125".
  On a machine with no ripper at all this dialog only repeats F1.
- **Fix:** suppress it while the ripper is missing, because setup installs the right build. When
  it does apply, use one sentence and one button: "A newer, tested ripper is available. Install
  it (about 3 minutes)?". Move the handshake detail to *Setup & Updates → Details*. Rule 1 also
  says an update offer goes in the window, as a banner or the status line, not in a modal.

**F3. Setup's failure and timing wording** (severity 3, effort M). This breaks *error-responses*,
*Messages for people* (what happened, what it means, what to do) and Nielsen's heuristic 9.

- **The failure:** `run3/04-HostSetupDialog-Set_up_Platterpus.png` shows "Setup stopped at
  "Distrobox": command not found: pkexec ([Errno 2] …)". The step list repeats it with an ×. The
  log path is plain text, not a link. The user isn't told what pkexec is or what to do. The step
  ran `pkexec apt-get install -y distrobox`, so on a desktop without polkit the first step is a
  dead end.
- **The timing:** the dialog says "On Bazzite/Silverblue everything's already there, so this is
  usually instant". The README (*Easiest*, step 3) says "It takes a few minutes: it creates the
  container and builds the ripper". The step list includes "Platterpus fork of cyanrip (build +
  export)".
- **Fix:** map each known failure to a sentence and an action. For example: "Couldn't ask for
  your password (pkexec is missing). Install Distrobox with your software centre, then press
  **Re-run setup**." Make the log path an **Open log** button. Give one honest estimate ("about 5
  minutes, mostly building the ripper") and show elapsed time while it runs.

**F4. The wizard opens with an empty box, and two windows share one title** (severity 2, effort
S). This breaks *usability-review* rule 3 and *windows-and-dialogs* rule 6.

- **Evidence:** the yes-or-no question and the wizard are both titled "Set up Platterpus"
  (`run3/01`, `run3/03`). The wizard opens with an empty white log box covering half its area
  (`run2/03`). The question ends "→ Run setup…." with a doubled full stop
  (`ui/main_window_provision.py:427`).
- **Fix:** title the question "Install the ripping tools?" and the wizard "Setup". Hide the log
  box until it has lines, or fill it with the step list before it starts. Drop the stray full
  stop.

**F5. The read-offset step** (severity 2, effort S). This breaks *windows-and-dialogs* rule 6,
Nielsen's heuristic 2 and *settings-and-options* rule 1.

- **Evidence:** `stage-light/H-drive-setup.png`. The text is good ("Known read offset for
  PIONEER … +667 … click "Save offset""). But a 200-px empty results box sits between the text
  and the control, because cyanrip can't detect offsets. The text also says "isn't available
  with this backend".
- **The default:** `override_read_offset` defaults to `False` (`config.py:176`), so until an
  offset is saved, rips aren't offset-corrected. Saving turns it on, and the tooltip says so.
  The checkbox's off state still reads as a trap to EAC users.
- **Fix:** hide the results box when detection isn't supported. Replace "backend" with "the
  ripper". Make **Save offset** the default button. Show "Offset applied ✓" beside the field
  once saved.

### The main screen

**M1. The hierarchy puts reference data above the task** (severity 2, effort M). This breaks the
aesthetic and minimalist design heuristic (8) and *interface-patterns*, *Width and density*.

- **Evidence:** `stage-light2/B-main-disc-loaded.png`. Seven label rows come first: Drive,
  MusicBrainz disc ID, CDDB disc ID, MusicBrainz match, AccurateRip, Read offset, Cache defeat.
  Then three album fields, then the track table. At 1000×860 the table shows 4 of 11 tracks. In
  the 752×752 window the app opens at (`run1/01`), it shows none.
- **Fix:** fold the disc IDs into a collapsible *Disc details* row, or move them to the Details
  tab. Keep Drive, Album and Read offset visible. Give the track table the stretch.

**M2. Two track tables and two progress bars** (severity 2, effort M). This breaks
*usability-review* rule 3 (one thing, one place).

- **Evidence:** `stage-light2/C-main-ripping.png` and `D-main-done-verified.png`. The top table
  has the columns Rip? # Title Artist Length Status. The *Tracks* tab below has # Title Status AR
  v1 AR v2 EAC. Both list the same tracks with different titles and statuses ("✓ Done" above,
  "ripped successfully" below). The bars are "Overall 38%", then a status line, then a second,
  unlabelled bar at 62%.
- **Fix:** use one track table. Add the verification columns after a rip and keep it the only
  list. Use one bar with "Track 5 of 11, 62%" in the status line.

**M3. During a rip, the Live log tab shows cyanrip's raw output** (severity 1, effort S).

- **Evidence:** `C-main-ripping.png` shows "Ripping and encoding track 4, progress - 100.00%",
  "Accurip: accurately ripped (confidence 37)".
- **Fix:** default to the track table, with the current row highlighted, and keep the log one
  click away.

**M4. Force stop sits beside Cancel at the same weight** (severity 1, effort S). This breaks
*windows-and-dialogs* rule 4 (the spirit of no easy destructive action).

- **Evidence:** `C-main-ripping.png`.
- **Fix:** show **Force stop** only after Cancel has been pressed and the countdown is running.
  The status text already describes the countdown (`main_window_rip.py:1262`).

### Verification verdicts and results

**V1. "Done." over a warning, with no next step** (severity 3, effort S). This breaks
*usability-review* rule 2 ("no verdict word … sits over a failure") and *error-responses*
(what to do).

- **Evidence:** `stage-light2/D-main-done-verified.png`:
  - The status line reads "01:39:22 · Done." (`main_window_rip.py:2125`).
  - The banner reads "⚠ 12 of 14 tracks verified exactly against AccurateRip; on the other 2,
    only one frame matched, so AccurateRip says each is WRONG (see the table)"
    (`verdict.py:785-797`).
  - The disc panel reads "AccurateRip says tracks 3, 5 are WRONG (only frame 450 matched, so the
    audio differs from the pressing)" (`track_proof.py:291`).
- **Fix:** make the status line carry the verdict ("Finished, 2 tracks need attention"). Give
  the banner one plain sentence and an action, for example: "2 tracks (3 and 5) don't match
  other people's rips of this CD. Clean the disc and **Re-rip these tracks**". Keep "frame 450"
  in the tooltip and report.

**V2. CTDB and AccurateRip disagree and nothing reconciles them on screen** (severity 2, effort
S). This is partly staged: the CTDB line is my match result, with no per-track data.

- **Evidence:** `E-main-done-details-tab.png` shows "CTDB: verified ✓ (confidence 212)" in amber,
  under a ⚠ Details tab. A non-expert sees "verified ✓" and "WRONG" for the same rip. The repo
  has a disagreement note (`tests/test_ctdb_disagreement_note.py`). Check that it shows up on
  this surface with real data.
- **Fix:** give one combined verdict line above both, saying which source wins and why.

**V3. The results table speaks the databases' internals** (severity 2, effort S). This breaks
Nielsen's heuristic 2.

- **Evidence:** `D-main-done-verified.png` has the columns "AR v1", "AR v2" and "EAC", and the
  cells "OK (129 of 200)", "one frame only (200)" and "B0D122E7 ✓" / "0D427962 ~". Nothing on
  screen says what 200 is, or what ~ means.
- **Fix:** use a single *Verified* column ("✓ 129 matching rips", "⚠ Mismatch"). Put the v1, v2
  and CRC detail in a column hidden by default (an EAC-style view toggle) and in tooltips.

### Wording and consistency

**W1. Title Case inside lists, sentence case everywhere else** (severity 1, effort S). This
breaks *usability-review* rule 3, KDE's sentence-case style for list items, and *writing-style*.

- **Evidence:** `run5/06-SettingsDialog-Settings.png` has "Fast Verified — Lossless, Fully
  Verified (AccurateRip + CTDB) [Recommended]", "Embed in FLAC — Art Inside Each Track" and
  "Adaptive Ladder — Fast, Slower Only if a Disc Needs It [Recommended]"
  (`goal_presets.py:141-147`). Next to them, checkboxes and buttons are in sentence case.
- **Fix:** write the items in sentence case and drop the square brackets: "Fast and verified
  (recommended)".

**W2. Internal vocabulary reaches the user** (severity 2, effort S). This breaks Nielsen's
heuristic 2.

- **Evidence:**
  - "handshake round 40" appears in `run5/07` (Setup & Updates, "Approved build: … from handshake
    round 40") and in `run2/05`.
  - "2 ok, 2 missing/needs-attention" and "numpy (Python package) 2.5.5" appear in `run2/04`.
  - `run5/11` (Diagnostics) shows "present=False version=(unknown) min_version_met=False".
  - "metaflac path:", "Overread:", "Disc ISRC:" and "Extra matching reads to trust a track:"
    appear in `run5/06` and `stage-light/I-settings-0-1.png`.
  - "~/.local/bin/cyanrip … ripping Distrobox container" appears in the User Guide's second
    section, *How it's wired* (`help_content.py:43`, `run5/09`).
- **Fix:** keep the version pair and handshake data in Diagnostics, which is for bug reports.
  Everywhere else say "Ripper: up to date (tested with this version)". Drop the Python packages
  from the user-facing summary. Move *How it's wired* to the end of the guide.

### Layout, type, colour and dark mode

**L1. Dark mode is handled well, but only at start-up** (severity 1, effort S). From the code;
not run live.

- **What works:** `ui/status_colours.py` picks light or dark variants measured for WCAG AA, and
  `stage-dark2/D` and `E` read well. There's no hard-coded palette, so Breeze applies.
- **The gap:** the colour is chosen "at the moment the style is set". No `PaletteChange` or
  `ThemeChange` handler exists in `src/`: a grep for `PaletteChange|ThemeChange|colorSchemeChanged`
  finds nothing. Switching Breeze to Breeze Dark with the app open leaves the dark-amber
  `#7d4e00` verdict text on a charcoal background.
- **Fix:** re-apply the status styles in `changeEvent` on `QEvent.PaletteChange`.

**L2. Setup & Updates uses full-width, 40-px-tall buttons for every action** (severity 1, effort
S).

- **Evidence:** `run5/07-SetupCenterDialog-Setup___Updates.png`. Seven equally loud buttons
  stack up, so nothing reads as primary, and the dialog needs scrolling at 560×736.
- **Fix:** use a two-column row per item: status on the left, a normal-size button on the right.

**L3. Settings scrolls horizontally, and the Diagnostics text box scrolls both ways** (severity
1, effort S). Evidence: `run5/06` and `run5/11`. Fix: let long path fields shrink, and wrap the
diagnostics text.

### Errors, empty and waiting states

**E1. A rip error is a plain grey line** (severity 2, effort S). This breaks *usability-review*
rule 4 (an error beside the thing it's about, saying what to do).

- **Evidence:** `stage-dark2/G-main-error.png`. `_on_rip_error` calls
  `set_status(f"Error: {message}")` (`main_window_rip.py:1720`). `set_status` applies no level,
  colour or icon (`rip_progress.py:923-941`). The fallback text is "Rip failed — no diagnosis was
  captured. See <path>", a path the user must copy by hand.
- **Fix:** render failures through the verdict banner at the `error` level, with ✖. Map common
  causes, such as permission denied on `/dev/sr0`, to a fix. Add an **Open log** button.

**E2. Cancelled state** (severity 1, effort S). `F-main-cancelled.png` reads "Rip cancelled by
user. Partial files may remain." That is honest, but it doesn't say where the files are or
offer to remove them. Fix: "Rip cancelled. 3 finished tracks are in <folder>; **Open folder** ·
**Delete partial files**".

**E3. Empty states** (severity 1, effort S).

- **Evidence:** `run1/01`. With no drive, the window shows "(no drives found)" plus seven "—"
  rows, an empty table and two 0% bars, all of which look like data.
- **Fix:** show one empty-state panel: "No CD drive found. Connect a drive, then press
  **Refresh**", or "Ripping tools not installed. **Set up…**".

### Settings

**S1. One 33-row form, no groups, presets that don't show what they set** (severity 2, effort M).
This breaks *settings-and-options* rules 2, 3 and 6.

- **Evidence:** `run5/06` and `stage-light/I-settings-0-1.png`; `settings_dialog.py` has 33
  `addRow(` calls. Goal, Naming, templates, Read offset, metaflac path, Output format, Picard,
  After rip, Logging, Cover art, Max retries, Overread, Disc ISRC, Extra matching reads, Read
  speed, CTDB, CTDB repair, Verify FLACs and EAC-style log all sit in one column.
- **The presets:** the Goal preset's help text says the effort options "snap to good values"
  (`settings_dialog.py:147`). Nothing on screen shows which rows it changed, or turns the label
  to "Custom".
- **Fix:** group the rows into *Output*, *Accuracy*, *After a rip* and *Advanced* (tabs or
  headed sections; KDE apps use a sidebar). Put the raw templates and `metaflac` path behind
  Advanced. Mark the rows a preset controls.

**S2. Read offset in Settings is a sentence, not a control** (severity 1, effort S).
`run5/06` reads "no drive selected: each drive keeps its own read offset / Set it in Tools →
Setup & Updates… → Set up drive…". That's honest, but it is a three-level path. Fix: a **Set up
drive…** button in the row.

### Accessibility and keyboard

- **A1.** Good: every button has a mnemonic. Quit is Ctrl+Q, Settings Ctrl+, and the User Guide
  F1. Progress bars and the status line have accessible names (`rip_progress.py:683-686`), and
  status changes are announced to screen readers without stealing focus.
- **A2.** No shortcut starts a rip apart from Alt+S (severity 1, effort S). EAC users expect F5
  or Ctrl+R style accelerators. Add one and show it in a *Rip* menu, which doesn't exist: the
  File menu holds only "Rip as Unknown Album…" and Quit.
- **A3.** The heaviest text, the verdict banner, is amber bold on grey. It passes AA by the
  module's own tests, but it also appears on the CTDB "verified ✓" line, so colour can't
  separate good from bad there (`E-main-done-details-tab.png`). See V2.

### Performance a user feels

- **P1.** The first-run setup builds the ripper from source in the container: "Platterpus fork
  of cyanrip (build + export)" in `run3/04`, and `deps/fork_source.py`. The README allows "about
  twenty minutes for the setup". The dialog shows a static bullet list with no progress or
  elapsed time before the first step ends (`run3/04`). Severity 2, effort M: show per-step
  progress and an estimate (F3).
- **P2.** The launch dependency check enters a cold container (per the comment at
  `app.py:1390`). It runs off-thread, and the window was responsive at once in every run. Good.

### Docs a user reads

**D1. The README's first screen is project history** (severity 3, effort S). This breaks
*writing-style*, *A README's sections* (the opening paragraph says what it does and for whom),
and *usability-review* rule 5.

- **Evidence:** `README.md` lines 1 to 14 hold 662 words in three blockquotes. Line 9, the
  *Status* paragraph, is 317 words: "round 31 approved that pair, and 0.7.103 is the first
  release that installs `.21` …". The second blockquote is about Overread on one Pioneer model.
  The third cites KDD-18 and KDD-32/33.
- **Also:** *At a glance* links `PLANNING.md §8 KDD-07`. The capability matrix lists upstream
  maintainers and PR numbers. "round", "KDD-" and "handshake" appear 40 times in the README.
- **Fix:** open with two sentences ("Platterpus rips audio CDs on Linux to verified FLAC, the
  way EAC does on Windows. Download one file and it sets itself up."). Follow with a screenshot
  and a 4-step *Install*. Then a one-line status: "Beta. Tested on Bazzite KDE; see
  CHANGELOG". Move the round history to `CHANGELOG.md` or `docs/`.

**D2. *Getting started* is buried** (severity 2, effort S).

- **Evidence:** `README.md:541`. Before it come *Fast path*, *Manual steps* and Steps 1 to 7
  (lines 155 to 540): Distrobox, the container, COPR and exports. These are for testers and
  developers.
- **The good part:** *Getting started* itself is clear, plain and well paced. It is also the
  in-app guide (`run5/08`).
- **Fix:** put *Getting started* straight after *Install*, and move the manual steps to
  `docs/manual-install.md`.

**D3. `docs/` has no user documents** (severity 1, effort S). `docs/README.md` opens with
"Single source of truth — where each kind of content lives", a maintainers' map, and the
directory is handshake, seam and rig material. A user who opens `docs/` finds nothing for them.
Fix: a top line in `docs/README.md` saying "Using Platterpus? Start at Help → Getting started,
or the README's *Getting started*".

## 3. What's already good: keep it

- **The *Getting started* guide** (`run5/08`, README line 541) is plain, ordered, names labels
  exactly as they appear, and gives honest times. It is generated from one source
  (`scripts/emit_getting_started.py`).
- **The read-offset auto-fill** from the AccurateRip drive list ("+667 … No disc needed") is the
  best first-run moment in the app.
- **Honest verdict logic:** a one-frame match is never shown as verified, a partial rip never
  claims "all N tracks", and the status names the timestamp. Simplify the words, not the logic.
- **Dark-mode status colours** are measured for WCAG AA on both themes (`ui/status_colours.py`),
  and every level carries a symbol as well as a colour.
- **Responsiveness and safety:** the dependency check runs off-thread, dialogs are parented and
  stacked deliberately (`ui/dialogs/stacking.py`), first-run offers are suppressed during
  scripted runs, and Cancel arms an automatic force-stop with a stated countdown.
- **Accessibility:** mnemonics, accessible names, and live announcements without focus theft.
- **The Uninstall dialog** says plainly what it removes and that music is never touched
  (`run5/13`).

## 4. Lessons for our skills

1. **windows-and-dialogs.** Rule 3 covers stacking but not *sequencing*. Here each dialog waits
   politely for the last, so the stacking checks pass, yet four arrive in a row. Add: "At
   launch, at most one dialog. Everything else waits as a banner in the main window." Add a
   *gui-testing* check: start fresh, answer No, and count the modals in the first 30 s
   (expected: zero).
2. **windows-and-dialogs / usability-review.** No rule says **a declined offer stays declined**,
   with no other path re-raising it in the same launch. F1 broke exactly that. Add it to rule 1,
   and to the *gui-testing* "Unasked" test.
3. **usability-review.** Rule 2 forbids "Done" over a failure, but this case is "Done." over a
   *warning*. Widen it: "no verdict word over a warning, either. The status line carries the
   verdict's level." Add: "a verdict a non-expert reads states the next action". Our modules
   never ask for the next step on a *result*, only on an *error* (error-responses).
4. **usability-review or a new onboarding section.** We have no rules for the **first five
   minutes**:
   - nothing before the first useful screen but what is needed;
   - an honest time estimate for setup, in one voice across the dialog and the docs (F3);
   - an empty state that says the next action (E3).
   The brief names a `platform-design` module, which doesn't exist under
   `user-experience/references/`. Either it should, or the brief should be corrected.
5. **error-responses.** *Messages for people* is written for HTTP APIs and services. Add a
   desktop line: "never show an exception's text (`[Errno 2]`, a Python repr) in a dialog. Map
   the known causes, and give an **Open log** button, not a path to copy."
6. **writing-style, *A README's sections*.** The template says what the opening paragraph holds,
   but not how long the first screen may be or what it must not hold. Add:
   - a limit, about 150 words before the first heading after the title;
   - no release history, internal decision IDs (KDD-NN) or process names above *Install*;
   - user content before tester and developer content.
   `prose-check` could flag a README whose first section is longer than a set word count.
7. **settings-and-options / usability-review rule 3.** Neither says a **combo-box or list
   item** follows the same case rule as labels. Title Case slipped into list items while the
   labels were sentence case. Add it to the consistency audit, as KDE's HIG does.
8. **settings-and-options rule 2.** "A preset shows the values it sets" is right, and was
   missed here. Add an audit step: pick each preset and check that the rows it changes are
   marked on screen.
9. **visual-theme, *Dark mode*.** This is written for CSS and tokens. Add the desktop half:
   colours chosen at start-up must be re-chosen on a live theme change (Qt's `PaletteChange`,
   GTK's `notify::dark`), and a test that flips the palette. Platterpus did the hard part
   (measured variants) and still missed this.
10. **usability-review, *What a review of the code can and can't judge*.** Add **vocabulary
    leakage** as something code review can catch mechanically. Grep the user-facing strings for
    the project's internal terms: here "handshake", "round N", "KDD-", "backend", "numpy",
    `present=False`. Today nothing in our modules prompts that grep.
11. **interface-patterns, *Width and density*.** Nothing warns about **duplicated lists**: the
    same tracks in two tables with different status words (M2). Add: "one list per subject.
    Add columns after an operation rather than a second table."
12. **gui-testing.** Add the recipe that made this review possible: run the real `main()`
    offscreen with `HOME` redirected and `subprocess.Popen` refused. Grab every top-level window
