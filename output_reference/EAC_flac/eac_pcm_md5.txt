WHY THIS FILE EXISTS
--------------------
This is the STRONGEST bit-perfection evidence we can hold, and it is pure text.

FLAC's STREAMINFO block carries an MD5 of the *unencoded* audio — the PCM the
encoder was handed. Two FLAC files whose STREAMINFO MD5s are equal decode to
byte-identical PCM. So comparing our rip's MD5 against EAC's is a DIRECT proof
of bit-identity, where comparing CRC32s is a proof about a 32-bit digest.

It also settles the shared-ancestor problem CLAUDE.md warns about. Comparing two
cyanrip runs compares relatives; comparing against EAC compares against an
independent implementation, on the same physical disc, in the same drive.

And it needs NO AUDIO TRANSFER, which is what makes it usable here at all
(critical rule #8 — never commit or move copyrighted media). One command
produces the comparable value:

    metaflac --show-md5sum *.flac

CORRECTION THIS FILE RECORDS
----------------------------
When these five files first arrived I described them as our rip's output and
reported that "each file's STREAMINFO sample count matches the log". They are
EAC's files. The measurement was right and the provenance was wrong, and the
corrected reading is *better* evidence than the one I claimed: EAC's own files
carry exactly the sample counts cyanrip's log reports for the same tracks, which
is two independent rippers agreeing on every track boundary.

HOW TO USE IT
-------------
Run the command above on our rip of this disc and compare per track.

  equal   -> our PCM is byte-identical to EAC's. Bit-perfect, proven directly.
  differ  -> a real difference in the audio, NOT a CRC-convention mismatch.
             That is worth a full investigation; start with the offset (+667)
             and the per-track CRCs in the cyanrip log.

A DIFFERING MD5 IS NOT AUTOMATICALLY OUR BUG: a track that legitimately matched
only the +450 offset-variant pressing may differ from a run whose offset landed
elsewhere. Read it alongside the AccurateRip results rather than alone.
